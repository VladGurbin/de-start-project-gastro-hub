# Аналитическая база данных ресторанного холдинга Gastro Hub

### Описание проекта
Проектирование, выстраивание реляционной архитектуры (DDL) и миграция сырых данных (DML) для крупной сети заведений общественного питания (рестораны, бары, пиццерии, кофейни). В рамках проекта реализован аналитический слой (Views/Materialized Views), написан комплекс сложных ad-hoc запросов для расчета бизнес-метрик холдинга, а также настроены механизмы безопасного изменения данных в транзакционном контуре.

### Технологический стек
* **СУБД:** PostgreSQL
* **Инструментарий разработки:** DBeaver, SQL (DDL, DML, TCL)
* **Методологии:** Оптимизация производительности (материализованные представления), полуструктурированный анализ (JSONB), оконная аналитика, управление блокировками (Row/Table-level locks).

---

### Архитектура базы данных и контур миграции (DDL / DML)

База данных развернута в кастомной схеме `cafe`. Логика сущностей разделена по следующим изолированным файлам в репозитории:

1. **`schema_and_types.sql` (Инициализация и DDL):**
   * Создание схемы `cafe` и кастомного перечисления типов заведений `restaurant_type` (Enum).
   * Проектирование реляционных таблиц с использованием автоматической генерации криптографически стойких идентификаторов `UUID` (`GEN_RANDOM_UUID()`) в качестве первичных ключей.
   * Выстраивание связей и ограничений целостности данных (`FOREIGN KEY`, `PRIMARY KEY`, `NOT NULL`, `UNIQUE`).
2. **`data_migration.sql` (Трансформация и миграция DML):**
   * Перенос и очистка данных из сырой схемы `raw_data` в целевую структуру.
   * Использование сложных агрегаций (`MIN/MAX` с `GROUP BY`) для автоматического вычисления исторических интервалов работы менеджеров в таблице `restaurant_manager_work_dates`.

---

### Аналитический контур холдинга (Скрипты и представления)

В проекте реализованы сложные ad-hoc сценарии, сохраненные в виде отдельных SQL-скриптов:

* **`view_top_avg_checks.sql` (Представление `cafe.bonus`):**
  Расчет топ-3 заведений с самым высоким средним чеком внутри каждого типа заведения. Реализовано на базе CTE и аналитической оконной функции фильтрации `RANK() OVER (PARTITION BY type)`.
* **`materialized_view_dynamics.sql` (Материализованное представление `cafe.dynamic_check`):**
  Анализ годовой динамики изменения среднего чека ресторанов в процентах. Для исключения повторных тяжелых расчетов данные кэшированы в материализованное представление. Расчет исторического смещения реализован через оконную функцию `LAG()`.
* **`manager_rotation_analysis.sql` (Скрипт анализа сменяемости кадров):**
  Аналитическое расследование частоты смены менеджеров в заведениях холдинга. Вычисляет количество уникальных ротаций через комбинацию `LAG()` и условной логики `CASE WHEN`, возвращая топ-3 заведений с нестабильным кадровым контуром.
* **`jsonb_menu_analysis.sql` (Анализ неструктурированного меню):**
  Скрипты для работы с типом данных `JSONB`. Демонстрируют глубокое владение полуструктурированными выборками: разворачивание JSON-ключей через `jsonb_each_text()`, поиск пиццерии с самым широким ассортиментом (`DENSE_RANK()`) и вывод самой дорогой пиццы в каждом заведении через `ROW_NUMBER()`.

### Контур транзакций и управление блокировками

Файлы этого блока демонстрируют навыки безопасной работы с данными в высоконагруженных системах (конкурентный доступ):

1. **`transaction_jsonb_update.sql` (Атомарное обновление цен):**
   * Скрипт безопасного повышения стоимости позиции «Капучино» на 20% во всех кофейнях. 
   * Обновление данных выполняется внутри изолированной транзакции (`BEGIN ... COMMIT`) с динамической генерацией путей обновления JSONB через `jsonb_set()`. 
   * **Механизм безопасности:** Автоматически применяется Row-level блокировка (`FOR UPDATE`) на изменяемые строки, защищая их от параллельной перезаписи другими транзакциями.
2. **`transaction_table_refactoring.sql` (Рефакторинг структуры таблиц):**
   * Миграция телефонной книги менеджеров на массивный тип данных (`text[]`) с одновременным удалением старого столбца.
   * **Механизм безопасности:** Ручной перевод таблицы в режим `LOCK TABLE ... IN SHARE MODE`. Блокировка разрешает чтение данных сервисами, но гарантированно запрещает любые параллельные изменения структуры и данных сторонними процессами до успешного завершения миграции (`COMMIT`).
